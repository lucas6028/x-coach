# Fitness-AQA 深度驗證實驗摘要

> 狀態:完成(2026-07-24)。五臂全數抽取完畢(MediaPipe 2D/3D、RTMPose 2D、
> NLF 2D/3D),NLF 在 Kaggle P100 上抽取,偵測率 98.7%,上下軸方向已驗證正確。
>
> **結論:在 Fitness-AQA 蹲深分類這個下游任務上,深度通道「不」改變分類結果**
> ——這與 Fit3D / REHAB24-6 的量測結論方向相反,但兩者其實一致,原因見下方解讀。

## 問題

Fit3D 與 REHAB24-6 有光學動作捕捉真值,深度誤差可以直接量測;結論是矢狀面的
深度判定受投影幾何破壞,而由影像直接回歸 3D 能取回深度軸。Fitness-AQA 沒有 3D
真值,是真實健身房的單機位手機影片,因此這裡只能問下游問題:**同一個偵測器、
同一組特徵、同一組切分,加上深度通道之後,分類結果會不會改變**。

## 資料選擇

用 `Squat/Labeled_Dataset/Shallow_Squat_Error_Dataset`,而不是影片層級的
`error_knees_forward` / `error_knees_inward`。理由:

- 這是逐幀的蹲深二分類,正是 Fit3D 上被量測到最受投影破壞的那個判定的野外版本。
  **標籤極性**:ReadMe 寫「0 = no error,1 = erroneous」,但實際看圖與量測都顯示
  `1` 類是**蹲得明顯較深**的幀(膝角中位 55° vs `0` 類 86.5°;髖低於膝 vs 髖高於膝),
  與資料夾名「shallow error」的字面直覺相反。對本實驗無影響——要問的是「加不加深度
  通道會不會改變分類」,與極性無關——但描述時一律當成「深/淺兩個深度類」,不硬套
  ReadMe 的 error/no-error 語意。人工檢視 test 各 8 張裁切圖確認此極性(class 1 明顯
  蹲到底,class 0 較淺或非蹲底)。
- 3,611 張蹲到底的單幀,不需要時序模型,也不需要 rep 切分,雜訊來源少。
- 官方 train/val/test id 清單彼此**影片不重疊**(train 440 / val 90 / test 93 支),
  切分洩漏不會膨脹比較結果。
- 類別接近平衡:全體 2,027 負 / 1,584 正。

輸入一律使用 release 自帶的 `crops_unaligned` 人物裁切圖。曾嘗試改用原始影片的
完整畫面(幾何條件較好),但把裁切圖對回來源影格在蹲底附近有 ±1 幀的模糊
(相鄰影格幾乎相同,樣板比對 8 例只有 1 例落在標註影格上),而各臂必須看到
逐位元相同的輸入,因此放棄完整畫面。

## 實驗臂

| npz | 來源 | 空間 | 意義 |
|---|---|---|---|
| `nlf_3d` | NLF `joints3d` | `cam3d`(mm) | 回歸出來的真深度 |
| `nlf_2d` | NLF `joints2d` | `image2d`(px) | **同一次前向傳播**,拿掉深度 |
| `mediapipe_3d` | BlazePose world landmarks | `cam3d`(mm) | 啟發式深度 |
| `mediapipe_2d` | BlazePose image landmarks | `image2d`(px) | 同一次推論,拿掉深度 |
| `rtmpose_2d` | RTMPose COCO-17 | `image2d`(px) | 強 2D 偵測器參考 |

能回答問題的是**同模型配對**:`nlf_3d` vs `nlf_2d`。跨模型比較(NLF vs MediaPipe)
把深度和偵測器品質混在一起,只當作背景資訊。

## 公平性設計

- **同樣的列**:任何一臂失敗的樣本,從所有臂一起剔除。
- **同樣的特徵**:`src/fitness_aqa/cue_features.py` 用 `src/fit3d/biomech.py` 的公式
  算 14 個無因次角度與比值;2D 與 3D 維度相同,3D 不會因為欄位比較多而佔便宜。
- **同樣的「上」**:`cam3d` 旋轉成垂直軸等於影像 `−y`,兩個空間對垂直的定義一致,
  差別只剩深度通道;兩者都不假設相機水平。
- **同樣的分類器**:L2 logistic regression,閾值在 val 上以 balanced accuracy 選定。
  故意用弱模型——要問的是特徵帶不帶得動訊號。
- **影片層級 cluster bootstrap**:同一支影片的多幀彼此相關,對幀重抽樣會假造精度。
  信賴區間與臂間差值都以整支影片重抽樣,並在相同 replicate 上配對。

## 解讀

**主要對比 `nlf_3d − nlf_2d = +0.003`(p=0.813)——在此任務上深度完全不改變分類。**
這乍看與 Fit3D / REHAB24-6「深度是瓶頸」相反,但拆開後三件事互相吻合:

1. **真正起作用的軸是偵測器品質,不是深度。** 三個強偵測器臂(nlf_2d、nlf_3d、
   rtmpose_2d)全部擠在 0.902–0.905,彼此差 <0.003 且不顯著;兩個 MediaPipe 臂
   落在 0.78–0.79。決定分數的是「用 NLF/RTMPose 還是 MediaPipe」(+0.12,p<0.001),
   不是「有沒有 z 通道」(+0.003,不顯著)。健全性檢查通過:nlf_2d ≈ rtmpose_2d
   (−0.002),兩個強 2D 偵測器群聚,先前 RTMPose 0.904 不是管線 artifact。

2. **深度是「多餘的」,不是被天花板擋住——直接量到。** 把 nlf_3d 與 nlf_2d 在同一批
   test 列上逐樣本比對:兩臂各錯 43 個,加深度後**修好 18、弄壞 18**,剛好互相抵銷;
   預測一致率 91.8%,分數相關 r = 0.943、rank r = 0.958。兩臂讀的是同一個訊號,不是
   「深度本來有用但沒 headroom」。這把 +0.003 從一個曖昧的空值升級成一個機制結論:
   **2D 與 3D 讀到的是同一個垂直線索。**

3. **為什麼同一個線索?蹲深本質是「垂直」關係,而垂直在影像平面裡是保留的。**
   深度(z,射向相機的軸)才是 2D 丟失的軸。Fit3D 量到的大誤差是**膝關節角度**
   (混了垂直與深度兩軸),而蹲深判定的核心是髖相對膝的**高度差**,這在任何非俯視
   視角的影像 y 軸上都讀得到。人工檢視也印證:兩類差在蹲多低(垂直),不在朝向相機
   的深度。因此 nlf_2d 的 `depth_ratio` / `hip_drop_ratio` 本來就帶得動分類。

4. **方法差異放大了這點:Fit3D 用固定生物力學閾值,這裡是「在同分布標註上訓練分類器」。**
   訓練分類器能吸收該視角分布下任何殘餘的 2D 訊號,固定閾值不能。Fit3D 表四的 76%
   翻轉是固定閾值的結果;換成學習式分類器,強 2D 偵測器就把差距補平了。

**一句話**:在這個下游、學習式、同分布的蹲深分類上,**深度不改變分類,偵測器品質才會**。

### 這對論文的意義:限定了跨模型故事

本實驗做了一件論文 REHAB24-6 分析沒做的事——**固定偵測器**再開關深度。論文的
NLF 0.668 vs MediaPipe 0.633 是**跨模型**比較,把「偵測器品質」與「深度品質」綁在
一起。這裡拆開來看:同偵測器開關深度 = +0.003(不顯著),換偵測器(NLF-2D vs
MediaPipe-2D)= +0.122(p<0.001)。因此論文那 0.035 的差,**至少有一部分是偵測器
品質而非深度**,不能全記在深度頭上。這比硬把結果凹成「與 Fit3D 一致」更誠實、也更
站得住腳:深度瓶頸是「線索精度 / 固定閾值判定」層級的真現象(Fit3D 直接誤差量測
已證),但在「訓練分類器 + 蹲深這種垂直判定」的下游設定,強 2D 偵測器即可追平真 3D。

## 執行紀錄

- NLF 抽取:本機 GTX 1660 Ti 驅動 512.78(CUDA 11.6)裝不了 NLF 需要的 torch
  cu121,CPU 路徑實測不可行(單張 `detect_smpl_batched` >15 分鐘,CPU 僅約 0.3 核,
  非算力受限)。改在 Kaggle P100 上跑,沿用 REHAB24-6 配方(torch 2.5.1+cu121、
  先 import torchvision、取面積最大的偵測框):kernel
  `haoping6028/fitness-aqa-shallow-nlf`,3,738 張裁切圖偵測率 98.7%,約 10 分鐘。
  輸出以 `scripts/fitness_aqa/ingest_shallow_nlf.py` 轉成 `nlf_3d` / `nlf_2d` 兩臂。
- 上下軸驗證:轉入 biomech world(z up)後髖高於踝的比率 99.97%,確認
  `(x,z,−y)` 映射正確,`depth_ratio` / `hip_drop_ratio` / `torso_lean` 可信。
- 健全性檢查通過:`nlf_2d` ≈ `rtmpose_2d`(−0.002,p=0.883),兩個強 2D 偵測器
  群聚,排除管線 artifact。

## 後續可做(非本問題必需)

1. 天花板:蹲深任務 2D 已飽和。若要在「有 headroom」的任務上再測深度增益,
   可改用 `error_knees_forward`(矢狀面、需要側視)或膝內扣(額狀面)當標的,
   並重現論文「依錯誤型態分流」的不對稱性。注意那是影片層級任務,granularity
   與本實驗不同。
2. 消融:做一組只用旋轉不變角度、拿掉所有高度比值的特徵,確認強偵測器的優勢
   不是來自裁切框尺度線索而是真姿態。

## 環境副作用與測試

- 為了裝 torchvision(NLF 本機路徑需要),pip 把共用 `.venv` 的 torch 從
  2.11.0+cpu 升到 2.13.0+cpu(兩者皆 CPU build)。**事後看這步其實非必要**——
  NLF 最後在 Kaggle 上跑,本機沒真的用到 torchvision。torch 2.13 下全套測試正常;
  若要還原成 2.11 是乾淨的一步,但非必需。
- `tests/` 全跑:619 passed,唯一失敗是
  `tests/test_analyze_endpoint.py::test_concurrent_analyses_are_bounded`。**已完整
  root-cause,與本次改動無關**:該測試在拿 semaphore 之前會先
  `await run_in_threadpool(settings.allowed_upload_suffixes)`,而這個呼叫在冷快取下
  會做 Supabase round-trip;本機實測耗時 **6.98 秒**,超過測試 5 秒的輪詢死線,
  五個 task 全卡在這裡還沒進到並發區,peak 因此到不了上限。把
  `allowed_upload_suffixes` stub 掉 → peak = 2 測試通過。這是既有 backend 程式
  (我沒動過)對 Supabase 網路延遲的敏感性,CI(該呼叫快)會過;與 torch 升級無關。
- 本次新增的兩個測試模組(`test_fitness_aqa_cue_features` 12 個、
  `test_fitness_aqa_depth_classify` 10 個)全通過。前者證明特徵函式在 3D 下視角不變、
  在 2D 下會被視角破壞——本實驗的核心對比的最小驗證。
