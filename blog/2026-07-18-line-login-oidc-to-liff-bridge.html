01背景

要看懂這次的變更,得先知道「用 LINE 登入」在幕後究竟發生了什麼事。以下先給新手一段較深的鋪陳,已經熟悉的人可以直接跳到與本次直接相關的部分。

深入背景(熟悉的讀者可略過)

如果你已經知道 OAuth/OIDC、JWT 簽章、Supabase Auth 與 LIFF 是什麼,請直接往下捲。

「用 X 登入」的本質:一張簽過名的身分證

當你在某個 App 按下「用 Google / LINE 登入」,背後跑的是一套叫 OAuth 2.0 / OpenID Connect(OIDC) 的協定。你被導去 LINE 的登入頁證明「我就是我」,LINE 接著發給這個 App 一張數位身分證,叫做 ID token。

這張身分證是一個 JWT(JSON Web Token):三段用點號隔開的 Base64 字串——標頭、內容(claims,像 sub 使用者唯一編號、name、picture)、以及最關鍵的簽章。簽章的用途,是讓收到 token 的一方能確認「這真的是 LINE 發的、中途沒被竄改」。

i簽章怎麼驗?兩種家族

JWT 的標頭裡有一個 alg 欄位,標明簽章用了哪種演算法。粗分兩大類:對稱式(如 HS256)用「同一把密鑰」既簽也驗;非對稱式(如 ES256、RS256)用「私鑰簽、公鑰驗」。這個區別,正是本次變更的核心。稍後細談。

Supabase Auth:幫你保管登入狀態的托管服務

這個 app(x-coach)用 Supabase 當後端資料庫與登入系統。它內建一個叫 GoTrue 的認證服務,負責發放 session——也就是一組 access token / refresh token。使用者的所有東西(訓練歷史、對話紀錄、管理員權限)都靠這個 session 綁定,並由資料庫的列級安全(RLS)把關。換句話說:沒有 Supabase session,使用者就等於沒登入。

LIFF:讓網頁跑進 LINE、也拿得到 LINE 身分

LIFF(LINE Front-end Framework)是 LINE 提供的前端 SDK。它最為人知的用途是把你的網頁「嵌」在 LINE App 內開啟;但一個常被忽略的事實是——LIFF 在一般外部瀏覽器也能運作。無論在哪,只要使用者完成 LINE 登入,你都能呼叫 liff.getIDToken() 拿到那張前面說的 LINE ID token。這個小事實,是本次修復的支點。

與本次變更直接相關的背景

在這次改動之前,x-coach 有兩條各自獨立的 LINE 登入路徑:

情境原本走的路結果
在 LINE App 內(LIFF) 後端橋接:liff.getIDToken() → POST /api/auth/line → 後端向 LINE 官方 verify endpoint 驗證 → 鑄造 Supabase session ✅ 可用(已有 34 個測試)
一般網頁 Supabase 的 Custom OIDC provider(provider 名 custom:line),走瀏覽器 OAuth 導向,由 Supabase 自己驗 LINE 的 token ❌ 一直失敗

使用者回報的症狀非常具體:能正確導去 LINE、也是對的 channel,但登入完導回 App 卻不是登入狀態,Supabase 裡也沒有任何使用者紀錄。網址列帶著這一串:

?error=server_error&error_code=unexpected_failure
&error_description=Error getting user profile from external provider

注意這個錯誤是 Supabase(GoTrue)丟的,不是 App 自己的程式碼。它發生在「用授權碼換到 token 之後、要取得使用者 profile 時」——這個時間點很重要,它幾乎排除了 Channel ID/secret 或 redirect 白名單設錯的可能。真正的兇手藏在更裡面。

03核心直覺

整個故事可以濃縮成一句話:LINE 用一把「只有它跟你共享的密鑰」簽身分證,而 Supabase 卻堅持要用「一把公開的鑰匙」去驗——兩者對不上,網頁登入注定失敗。

兇手的名字:去 Supabase 後台撈到的那一行 log

網址列上那句 Error getting user profile 只是被包過的泛用訊息。真正的內部錯誤只在 Supabase 的 Auth Log 裡,長這樣:

failed to verify ID token: oidc: id token signed with unsupported
algorithm, expected ["ES256"] got "HS256"

一句話破案。Supabase 期待 ES256,但 LINE 給的是 HS256。

為什麼「期待 ES256,拿到 HS256」是死局

HS256 — 對稱式(LINE 用這個)

🔑只有一把密鑰:LINE 的 channel secret。
✍️用這把密鑰簽。
🔍要驗,得握有同一把密鑰(HMAC)。

ES256 — 非對稱式(Supabase 想用這個)

🔐私鑰簽(發行方保管)。
🔓公鑰驗(放在公開的 JWKS,人人可取)。
🌐驗證方不需要任何秘密。
圖一:兩種簽章家族。對稱式要「同一把秘密」才驗得動;非對稱式靠公鑰,誰都能驗。

Supabase 的 custom OIDC provider 是這樣運作的:它讀 LINE 的探索文件(access.line.me/.well-known/openid-configuration),看到裡面宣告 id_token_signing_alg_values_supported: ["ES256"],於是它只準備用「公鑰(JWKS)」去驗 ES256。

但實際上 LINE 發的 token 是用 HS256 簽的——要驗它,得拿 channel secret 當 HMAC 金鑰。Supabase 的 OIDC 流程裡沒有地方能叫它「改用那把密鑰去驗」。這不是設定沒調對,而是結構上驗不動。這也正是網路上「LINE + Supabase custom OIDC」屢屢失敗的原因。

!關鍵結論

沒有任何 Supabase 後台設定能修好網頁 OIDC 路徑。這條路必須整條換掉。

為什麼「橋接」那條路從來沒中招

回頭看 App 內那條早就能用的橋接:後端不自己驗簽章,而是把整張 token 丟給 LINE 官方的 verify endpoint(api.line.me/oauth2/v2.1/verify)。LINE 自己當然握有那把 channel secret,所以無論它用 HS256 還是 ES256 簽,LINE 都驗得動。演算法不相容的問題,在這條路上根本不會發生。

支點:LIFF 在「外部瀏覽器」也能用

那網頁怎麼辦?這裡用上前面埋的那個小事實:LIFF 不只在 LINE App 內能用,在一般瀏覽器也能。在網頁上呼叫 liff.login() 會把使用者導去 LINE 登入,回來後 liff.getIDToken() 一樣給你一張標準 LINE ID token。

於是解法水到渠成:網頁不要再用 Supabase OIDC,改用跟 App 內完全同一條橋接。

意外的紅利:兩條路合而為一,帳號不再分裂

還有一個沒明說、卻很要命的好處。舊的 OIDC 路徑,Supabase 會替 LINE 使用者建立一列 identities(provider = line);而橋接路徑建立的是「用合成 email line_<sub>@line.invalid 標記」的使用者。兩種建帳機制不相容——同一個人用網頁 vs. 用 App 內登入,會變成兩個不同的 Supabase 帳號、兩份歷史,而且永遠對不起來。

把網頁也導進同一條橋接後,兩邊都以 sub 衍生同一個合成 email → 同一人不論從哪進來都是同一個帳號。修 bug 的同時,順手拆掉了一顆未爆彈。

順帶處理的三件小事

A一次性 guard 的死鎖 bug

網頁登入的「成功」其實是在頁面重導回來後的 auto-login effect 裡完成的(那時已經沒有按鈕的 click handler 了)。舊碼只在按鈕分支清掉「一次性重導旗標」LIFF_RELOGIN_KEY,忘了在 effect 裡清。結果:登入成功 → 登出(會順手 liff.logout() 讓 isLoggedIn() 變 false)→ 下次登入撞上還沒清掉的旗標而死鎖,直到關掉分頁。修法:在 effect 拿到 session 後也清旗標,並在 signOut 再清一次保險。

B「LINE 登入中…」指示器

網頁重導回 /app 後,session 要等 liff.init() + 後端橋接跑完(數秒)才到位。這幾秒 header 右上角原本顯示「登入」連結——看起來像壞掉。新增一個 lineAuthenticating 狀態,在交換進行時顯示轉圈的「LINE 登入中…」。

C官方 LINE 標誌

登入頁的 LINE 按鈕原本用一個簡化的白色氣泡。改成 LINE 官方標誌(品牌綠圓角方塊 + 白色氣泡 + 綠色「LINE」字),直接把官方 SVG 的向量路徑內嵌進來(不外連圖片——app 的 CSP 會擋外部圖片)。

04程式碼走讀

改動集中在前端。核心是 frontend/src/lib/auth.tsx;其餘是 UX、效能、圖示與文件的收尾。以下依「先骨幹、後枝節」的順序走一遍。

群組一:核心改道——網頁登入從 OIDC 換成 LIFF 橋接

先刪掉那個再也用不到的 OIDC provider 常數,並把 signInWithLine 的網頁分支整段重寫。關鍵轉折:判斷條件從 isInClient()(只在 LINE App 內)放寬成 isLoggedIn()(在外部瀏覽器完成登入後也為真),於是同一段程式同時服務 App 內與網頁。

// Supabase custom OIDC provider slug for LINE …
const LINE_OAUTH_PROVIDER = "custom:line" as const;

const signInWithLine = useCallback(async () => {
  const liff = await initLiff();
  if (!liff) throw new Error("LINE sign-in is not available.");

  // 尚未 LINE 登入(外部瀏覽器第一次點):交給 LINE 的登入重導。
  if (!liff.isLoggedIn()) {
    if (sessionStorage.getItem(LIFF_RELOGIN_KEY) === "1")
      throw new Error("LINE sign-in failed. Please try again later.");
    sessionStorage.setItem(LIFF_RELOGIN_KEY, "1");
    liff.login({ redirectUri: `${window.location.origin}/app` });
    return;
  }

  const idToken = liff.getIDToken();          // 已登入:直接拿 token
  // … POST /api/auth/line → client.auth.setSession(minted) …
  // 舊的網頁 fallback:Supabase custom OIDC 導向(整段刪除)
  await client.auth.signInWithOAuth({ provider: LINE_OAUTH_PROVIDER, … });
}, []);

接著,把「靜默自動登入」的 effect 也放寬,讓它同時涵蓋兩種情境:App 內(本來就已登入)與網頁重導回來的那一趟。這一步是「一鍵完成」網頁登入的關鍵——回到 /app 後,沒有按鈕了,就靠這個 effect 把交換收尾。

const liff = await initLiff();
if (!active || !liff?.isInClient()) return;
if (!active || !liff?.isLoggedIn()) return;   // 網頁重導回來時也成立
const idToken = liff.getIDToken();
if (!idToken) return;

登出也要對稱處理。在外部瀏覽器,LIFF 會自己記住登入狀態;若不一起清掉,auto-login effect 會在下次載入時把使用者「偷偷登回去」,破壞明確的登出。因此網頁登出時順手 liff.logout()(App 內則保留,那裡「開啟即登入」是刻意的行為)。

await supabase.auth.signOut();
sessionStorage.removeItem(LIFF_RELOGIN_KEY);     // 見群組二
const liff = await initLiff();
if (liff && !liff.isInClient() && liff.isLoggedIn()) {
  try { liff.logout(); } catch { /* best-effort */ }
}

群組二:修掉一次性 guard 的死鎖

如前所述,網頁登入的成功發生在 auto-login effect,而非按鈕。舊碼只在按鈕分支清 LIFF_RELOGIN_KEY。補上 effect 裡的清除(以及群組一 signOut 的保險清除),就能讓「登入 → 登出 → 再登入」的循環不再卡死。

const minted = await api.lineLogin(idToken);
await supabase!.auth.setSession(minted);
// 網頁流程真正在此完成 → 清掉一次性旗標,否則下次登入會死鎖
sessionStorage.removeItem(LIFF_RELOGIN_KEY);

!測試為何原本抓不到

單元測試的 beforeEach 每次都清 sessionStorage,所以「成功 → 登出 → 再登入」這條跨越三步的鏈路從未被連起來測。新增的回歸測試特地把這條循環走完一遍。

群組三:「LINE 登入中…」指示器

三個檔案協力:auth.tsx 暴露狀態、Header.tsx 顯示、i18n.tsx 加字串。狀態只在真正開始交換到結束之間為真,用 try/finally 精準開關。

// auth.tsx — auto-login effect
if (active) setLineAuthenticating(true);
try {
  const minted = await api.lineLogin(idToken);
  await supabase!.auth.setSession(minted);
} catch { /* silent */ }
finally { if (active) setLineAuthenticating(false); }
// Header.tsx — 右上角三態
{user ? (
  <AccountMenu />
) : lineAuthenticating ? (
  <span aria-live="polite"><CircleNotch className="animate-spin" /> {t("account.lineSigningIn")}</span>
) : (
  <Link to="/login">{t("account.signin")}</Link>   // 原本只有這個
)}

群組四:砍掉多餘的往返、提早暖機

auto-login 原本會先打一次 GET /api/health 確認橋接有沒有設定,再打 POST /api/auth/line——兩次循序的往返(透過 ngrok 隧道更貴)。health 其實多餘:沒設定的橋接本來就會在 lineLogin 回 503 並被吞掉。移除它,每次登入省一趟。

const health = await api.health().catch(() => null);
if (!active || !health?.line_login_configured) return;
const minted = await api.lineLogin(idToken);   // 未設定則回 503,照樣吞掉

另外在 main.tsx 開機時就先觸發 initLiff()(fire-and-forget、有快取),讓 LIFF SDK 載入與 LINE 換 token 的那 ~1.5 秒與頁面首次繪製重疊,而不是等頁面畫完才開始。

import { initLiff } from "./lib/liff";
void initLiff();   // 提早暖機,與首屏並行

群組五:官方 LINE 標誌

登入頁 Login.tsx 把原本簡化的 LineBubble 換成逐路徑內嵌的官方標誌 LineLogo(綠圓角方塊 + 白氣泡 + 綠色「LINE」字)。內嵌而非外連,是因為 app 的 CSP 會擋外部圖片,內嵌也能在任何尺寸維持銳利。

<LineBubble />              // 簡化的白色氣泡
<LineLogo size={20} />      // 內嵌的官方 LINE 標誌 SVG
