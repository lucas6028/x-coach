MediaPipe 怎麼跑在手機上？

深度科普 · 約 3,600 字 · 5 張圖 · 2026-07

一句話：MediaPipe 把「即時感知」拆成一張會流動的資料流圖——一顆顆 calculator 處理帶時間戳的 packet；它把最重的神經網路推論交給 GPU，而且從相機貼圖到畫面繪製，整條 pipeline 都待在 GPU 上不落地到 CPU；再用「偵測一次、之後只追蹤」的設計，才擠進手機上每幀只有十幾毫秒的殘酷預算裡。

為什麼「在手機上跑」這麼難

你打開一個健身 App，鏡頭對著自己深蹲，畫面上即時浮出一副骨架，關節角度隨你的動作跳動。這件事看起來理所當然，但底下藏著一個很緊的約束：即時。

螢幕要看起來流暢，畫面得穩定在 30 FPS 甚至 60 FPS。而 FPS 直接決定了每一幀你能花多少時間運算——這是純粹的算術：

$$ \text{每幀預算} = \frac{1000\,\text{ms}}{\text{FPS}} \quad\Rightarrow\quad 30\,\text{FPS} \approx 33\,\text{ms},\; 60\,\text{FPS} \approx 17\,\text{ms} $$

十幾到三十幾毫秒，要塞進「相機取像 → 影像前處理 → 跑一個神經網路 → 解碼輸出 → 疊圖繪製」一整條流程。過去要在手機上做到這件事，你有兩條路，兩條都不好走：

  • 送到雲端算：把每一幀傳到伺服器跑模型再傳回來。網路來回動輒上百毫秒，即時免談；還得一直連網、把使用者的影像上傳（隱私疑慮），伺服器成本也高。
  • 自己手刻端上 pipeline：用 OpenGL、相機 API、推論引擎（如 TFLite）從頭串。你得自己處理多執行緒、GPU 與 CPU 之間的資料搬運、掉幀時的緩衝、Android 跟 iOS 兩套幾乎重寫。每個 App 都重造一次輪子。

MediaPipe（Google 2019 年開源，見其框架論文）就是為了把第二條路變成一個可重用的框架而生：你描述「資料怎麼流」，它負責把流程高效、跨平台、即時地跑起來。這篇文章要拆的，就是它憑什麼能在一支手機上做到這件事。

核心直覺：一張會流動的圖

關鍵洞見

不要把感知程式寫成「一個從頭跑到尾的函式」，而是描述成一張資料流圖（dataflow graph）：節點是運算單元，資料像水一樣、帶著時間戳，順著邊流過去。框架負責排程、同步、搬運與掉幀——你只描述形狀。

打個比方。傳統寫法像一個人在廚房從備料、下鍋到擺盤一手包辦，做完一盤才能做下一盤。MediaPipe 像一條壽司輸送帶：每個師傅（calculator）只做一件事，盤子（packet）帶著號碼牌（timestamp）在帶子（stream）上流過去，前一站做完自動送到下一站。相機每吐一幀就上一盤，各站同時在忙不同的盤子——這就是管線化（pipelining），也是即時吞吐的來源。

這個「圖」的抽象帶來三個對手機至關重要的好處，我們接下來逐一拆開：(1) 模組化讓重活可以被單獨調度到 GPU 或獨立執行緒；(2) 時間戳讓多路資料能正確對齊、又能在算不過來時安全地掉幀；(3) 統一的 GPU 緩衝抽象讓資料整條路待在 GPU 上、不必來回搬。

機制一：Graph、Calculator、Packet、Stream

MediaPipe 的四個基本詞，一次講清楚：

  • Packet（封包）：資料流動的最小單位。一個 packet = 一個時間戳 + 一份唯讀的資料（可以是任何 C++ 型別：一張影像、一組地標、一個張量）。唯讀加上引用計數，意味著同一份資料可以安全地被多個節點共用，不必擔心誰改壞了誰——這也是它多執行緒安全的基礎。
  • Stream（資料流）：一串時間戳遞增的 packet。就是輸送帶。
  • Calculator（計算單元）：圖的節點，真正幹活的地方。每個 calculator 實作四個方法：GetContract() 宣告吃什麼、吐什麼型別；Open() 初始化；Process() 每當輸入齊了就被呼叫一次；Close() 收尾。框架保證同一個 calculator 同時最多只在一條執行緒上跑，所以你寫 calculator 時幾乎不用煩惱鎖。
  • Graph（圖）：把 calculator 用 stream 接起來的有向圖，用一份 protobuf 設定檔（.pbtxt）描述拓樸。還能把一整塊圖包成子圖（subgraph）當成一個節點重用——BlazePose 這種方案，本質上就是別人幫你組好、封裝好的一張子圖。

機制二：時間戳同步與「掉幀但不塞爆」

把運算拆成非同步流動的節點，馬上帶來兩個問題：對齊與塞車。MediaPipe 用同一把鑰匙解決——時間戳。

時間戳就是同步的鑰匙

假設一個節點要同時吃「原始影格」和「偵測結果」兩條流，把結果疊回影格上。這兩條流的 packet 到達時間不一定同步（推論比較慢）。MediaPipe 保證：只要兩條流上帶著同一個時間戳的 packet，它們一定會被湊在一起、在同一次 Process() 裡處理，不管它們在真實時間中誰先到。

關鍵概念是「已定（settled）時間戳」：當框架能確定某時間戳要嘛已經有 packet、要嘛保證不會再來，這個時間點就「定了」，節點才會被觸發。所以整張圖的執行是去中心化的——沒有全域時鐘，不同節點可以在同一瞬間處理不同時間戳的資料，這正是管線化吞吐的由來。

為什麼這對手機重要

物件偵測這類方案會讓「慢的偵測分支」跳幀跑、「快的追蹤分支」每幀跑，最後靠時間戳把偵測結果對回正確的相機影格。框架論文說這等於動態地把模型延遲藏起來——使用者看到的疊圖始終貼齊當下畫面，即使模型本身跟不上每一幀。

算不完的時候：反壓與丟包

手機算力會波動（發熱降頻、其他 App 搶資源）。如果相機一直以 30 FPS 灌資料、而推論只跑得動 15 FPS，未處理的 packet 會越積越多，延遲雪崩、記憶體爆掉。MediaPipe 的兩道防線：

  • 反壓（back-pressure）：當某條流的緩衝滿了，框架會回頭節流上游，避免無限堆積，同時維持確定性、避免死結。
  • 流量限制器（FlowLimiterCalculator）：這是即時應用的靈魂。它守在推論前面，若下游還在忙，就直接丟掉新來的影格而不是排隊。寧可少算幾幀，也不要讓延遲累積——對「看起來即時」而言，低延遲比不掉幀重要得多。

機制三：讓運算待在 GPU 上（真正的手機關鍵）

前面兩節其實是 MediaPipe 的跨平台底盤，桌機也適用。真正讓它「在手機上跑得動」的，是這一節：如何壓榨手機 GPU。

為什麼一定要用 GPU

手機 GPU 的浮點吞吐遠勝 CPU。Google 的 TFLite GPU 論文舉例：一支 Galaxy S9 上，CPU 約 270 GFLOPS，GPU（FP16）約 730 GFLOPS（此為該論文舉的單機範例，實際依機型而異）。更重要的是，用 GPU 跑推論還能省電、避免 CPU 過熱降頻——這對要連續跑好幾分鐘的健身或相機 App 是生死問題。

TFLite 的 GPU 加速走的是圖形標準 API而非各家私有介面：Android 用 OpenGL ES 3.1+、iOS 用 Metal，換取廣泛的裝置覆蓋。模型的張量會被鋪進 GPU 的貼圖／緩衝，論文還設計了一種 PHWC4 記憶體佈局（把通道每 4 個打包成一片），讓相鄰的 GPU 執行緒存取連續記憶體、命中同一條快取線。

魔鬼在工作組大小

不同 GPU 架構對 compute shader 的「工作組（work group）」大小極度敏感：論文指出在 Qualcomm Adreno 上調錯可能慢上 5–7 倍，而 Arm Mali 則相對穩健。這類硬體特化的髒活，正是框架幫你吞掉、讓上層 App 不必碰的東西。

Delegate：GPU 跑得動的就給 GPU

MediaPipe 用 InferenceCalculator 包住 TFLite，並依硬體自動選後端（CPU、GPU、或 CPU 上的 XNNPACK 高速核心）。TFLite 的 delegate 機制會先看模型裡哪些算子 GPU 支援，把圖切成子圖、支援的丟給 GPU「delegate 節點」，不支援的留給 CPU。搭配量化（GPU 上常用 fp16、CPU/NNAPI 路徑可用 int8），進一步壓低延遲與記憶體。

整條路待在 GPU 上：zero-copy

這是最關鍵、也最容易被忽略的一點。相機的影格本來就以 GPU 貼圖形式進來；如果每個步驟都把資料從 GPU 下載到 CPU、算完再上傳回 GPU，光是這些來回搬運就會吃光你的毫秒預算。

MediaPipe 用一個不透明的 GpuBuffer 型別代表 GPU 上的影像，並讓 GPU 節點之間「傳遞影格資料要快、不能有昂貴的複製」。GPU calculator 之間直接共用貼圖（zero-copy），跨 GL context 的同步則靠框架自動插入的 OpenGL fence——「能在 GPU 命令流裡同步就不強迫 CPU 等」。只有真的需要 CPU 處理時，才用 GpuBufferToImageFrameCalculator 這類轉換節點落地。

走一遍：BlazePose 姿態偵測

把前面所有機制兜起來看一個真實方案：BlazePose，MediaPipe 的人體姿態偵測（也是 x-coach 深蹲分析背後用的東西）。它從單張影格回歸出 33 個 身體地標。

直接對整張畫面跑一個能精準定位 33 點的網路太慢，塞不進每幀預算。BlazePose 的解法是拆成兩階段的偵測器—追蹤器（detector–tracker）管線：

  1. 偵測器（detector）：一個從 BlazeFace 衍生的輕量單人偵測器，先找出畫面裡人體的感興趣區域（ROI），並回歸出髖部中點、外接圓半徑、軀幹傾角等對齊參數。
  2. 追蹤器（tracker）：拿到對齊、裁切後的小圖，一次回歸 33 個地標座標、一個「人是否還在」的信心分數，並預測下一幀的 ROI。
關鍵：偵測只跑一次

整套設計的省力來源是——偵測器只在第一幀（或追丟後）跑。之後每一幀，系統直接用上一幀預測出的 ROI 餵給追蹤器，跳過昂貴的偵測。人在連續影格間不會瞬移，所以這個假設幾乎總是成立。這正是把「每幀都要重新找人」的成本攤平掉的關鍵。

官方回報這套在多數現代手機上能達到即時：Lite 版在 CPU（XNNPACK）上約落在 30 FPS 量級、Full 版稍慢，改用 GPU 則更快到能再串下游模型（確切數字依機型與版本而異，見官方部落格）。

最小實作：一段 graph 設定

要抓住 MediaPipe 的精髓，看它的圖設定檔比看呼叫程式碼更直接——執行模型全寫在裡面。下面是一段精簡的 .pbtxt，展示流量限制器 + GPU 推論這兩個手機關鍵：

# 相機影格進來（GpuBuffer 串流）
input_stream: "input_video"
output_stream: "pose_landmarks"

# 1) 流量限制器：下游還在忙就丟掉新影格，寧可掉幀也不累積延遲
node {
  calculator: "FlowLimiterCalculator"
  input_stream: "input_video"
  input_stream: "FINISHED:pose_landmarks"   # 回饋：告訴它「上一幀處理完了」
  input_stream_info: { tag_index: "FINISHED" back_edge: true }
  output_stream: "throttled_video"
}

# 2) 前處理：在 GPU 上把影像縮放/轉成模型輸入張量
node {
  calculator: "ImageToTensorCalculator"
  input_stream: "IMAGE_GPU:throttled_video"
  output_stream: "TENSORS:input_tensors"
  options: {
    [mediapipe.ImageToTensorCalculatorOptions.ext] {
      output_tensor_width: 256
      output_tensor_height: 256
    }
  }
}

# 3) 推論：TFLite + GPU delegate。跑不動的算子自動回落 CPU
node {
  calculator: "InferenceCalculator"
  input_stream: "TENSORS:input_tensors"
  output_stream: "TENSORS:output_tensors"
  options: {
    [mediapipe.InferenceCalculatorOptions.ext] {
      model_path: "pose_landmark.tflite"
      delegate { gpu {} }                    # <- 手機上的關鍵一行
    }
  }
}

注意那條 FINISHED 回饋邊（back_edge: true）：它讓流量限制器知道推論何時空出來，才能決定下一幀要放行還是丟掉。這就是「掉幀但不塞爆」在設定檔裡的長相。

如果你是用高階的 Tasks API（現行推薦介面，取代已棄用的 mp.solutions），上面整張圖被包成一個物件，呼叫端只剩幾行：

from mediapipe.tasks import python
from mediapipe.tasks.python import vision

# 建立 landmarker：指定模型 + 在 GPU 上跑 + 影片串流模式
options = vision.PoseLandmarkerOptions(
    base_options=python.BaseOptions(
        model_asset_path="pose_landmarker.task",
        delegate=python.BaseOptions.Delegate.GPU),
    running_mode=vision.RunningMode.VIDEO,   # 串流模式會自動用偵測器→追蹤器
)
landmarker = vision.PoseLandmarker.create_from_options(options)

# 每一幀丟進去（時間戳讓框架做追蹤器的 ROI 回饋）
result = landmarker.detect_for_video(mp_image, timestamp_ms)
for lm in result.pose_landmarks[0]:
    print(lm.x, lm.y, lm.z, lm.visibility)

至於加速幅度：Google 的 TFLite GPU 論文回報，相對 CPU 推論，GPU 在多種網路上約有 2–9× 的加速（依模型與機型而異）。把這個乘數，套到上面那張只有十幾毫秒的預算上，你就懂為什麼「用不用得到 GPU」常常直接決定了一個端上感知 App 做不做得成。

那在「手機瀏覽器」裡呢？

前面講的都是原生 App（Android 的 OpenGL ES / NNAPI、iOS 的 Metal）。但很多產品——包括 x-coach 在 LINE 裡的 LIFF 網頁——是跑在手機瀏覽器裡的。這時候沒有 OpenGL ES、沒有 NNAPI，MediaPipe 怎麼辦？

機制相同，後端不同

好消息是：圖、calculator、偵測器→追蹤器這套執行模型完全一樣，換掉的只是最底層的加速後端。MediaPipe 的 Web 版（Tasks for Web / 早期的 JS Solutions）把 C++ 框架編成 WebAssembly（WASM） 跑在瀏覽器，推論則走 WebGL、或新一代的 WebGPU 來吃手機的 GPU。「端到端待在 GPU、不落地到 CPU」的原則，在瀏覽器裡靠 WebGL 貼圖同樣成立。

層次原生 App手機瀏覽器（如 LIFF）
框架執行原生 C++C++ 編成 WebAssembly
GPU 推論後端OpenGL ES / MetalWebGL / WebGPU
CPU 推論後端XNNPACK / NNAPIWASM SIMD（＋XNNPACK）
圖 / calculator / 偵測器–追蹤器完全相同

對 x-coach 這種情境，實務上的意義是：你在瀏覽器裡拿到的其實是同一套 BlazePose 子圖，效能瓶頸會落在「這支手機的瀏覽器有沒有給到 WebGL/WebGPU 加速」以及「相機影像能不能不落地地餵進 GPU」。理解原生版的機制，等於理解了網頁版該去盯哪裡。

優缺點與適用場景

什麼時候該用 MediaPipe：

  • 要在端上（手機／瀏覽器）做即時串流感知——姿態、手部、臉部、影像分割、物件追蹤。
  • 想跨 Android／iOS／Web 用同一套邏輯，不想每個平台重刻 pipeline 與 GPU 搬運。
  • 需要現成、調校好的方案（BlazePose 等）當積木，快速做出 demo 再逐步替換 calculator。

它的代價與侷限：

  • 思維要轉成資料流：習慣寫循序程式的人，一開始會覺得「圖 + 時間戳 + 反壓」很陌生，除錯也得看 packet 在流裡怎麼跑（框架提供 tracer/visualizer 幫忙）。
  • 掉幀是特性不是 bug：即時模式下框架會主動丟幀。要每幀都算到、不能丟的離線批次分析，就得改用確定性模式或別的工具。
  • 模型不是萬能：偵測器→追蹤器假設「人不會在幀間瞬移」；快速大幅度移動或追丟時會回頭重跑偵測、短暫掉一下。單目 2D 地標也拿不到真正的深度（這正是 x-coach 一系列實驗撞到的天花板）。
一句話收束

MediaPipe 讓「手機上的即時感知」從一件每個團隊都要手刻的苦工，變成描述一張圖。真正跑得動的祕密不在單一神經網路多聰明，而在整個系統設計：把重活丟 GPU、讓資料整條路不落地、用時間戳對齊又敢掉幀、能偵測一次就絕不每幀重算。
